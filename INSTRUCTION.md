# Инструкция по использованию обработки kd2_merge.py

## Назначение

`kd2_merge.py` — скрипт для интеллектуального слияния файлов **правил Конвертации Данных 2 (КД2)** 1С.

**Проблема, которую он решает:** обычные инструменты сравнения (git diff, Beyond Compare, kdiff3) сравнивают файлы по номерам строк. Когда в одном файле добавляются строки, все последующие строки «съезжают», и инструмент начинает сравнивать **разные сущности** между файлами — возникает «мясорубка».

**Решение:** скрипт разбирает XML-файлы на сущности (Группа, Правило, Свойство, Значение, Алгоритм, Параметр, Обработка) и сопоставляет их по **идентичности** (Наименование, Код, Источник, Приемник), а не по позиции. Сравнение происходит только внутри одной и той же сущности.

---

## Требования

- **Python 3.x** (проверьте: `python --version`)
- Файлы правил КД2 в формате XML (с BOM или без)

---

## Структура проекта

| Файл | Описание |
|---|---|
| `kd2_merge.py` | Основной скрипт слияния |
| `decisions.txt` | Файл решений по спорным блокам (создаётся автоматически) |
| `merge_report.md` | Отчёт о слиянии (создаётся автоматически) |
| `*(develop).xml` | Актуальная версия из git — **основа результата** |
| `*(изменения).xml` | Ваш файл с правками — **источник ваших изменений** |
| `*(merged).xml` | Результат слияния (создаётся скриптом) |

---

## Роли файлов

| Роль | Файл | Зачем нужен |
|---|---|---|
| **develop** | `*(develop).xml` | Актуальная версия из git. Является **основой результата**. |
| **mine** | `*(изменения).xml` | Ваш файл с правками. Отсюда берутся **ваши изменения**. |
| **ancestor** (необязательно) | `base.xml` | Общий предок (`git merge-base`). Включает честный **3-way** merge. |
| **результат** | `*(merged).xml` | Итоговый файл — develop + ваши правки. |

---

## Статусы сущностей

| Статус | Значение | Что происходит |
|---|---|---|
| `need` | **ТРЕБУЕТ РЕШЕНИЯ** | Меняли обе стороны. Нужно вручную выбрать версию в `decisions.txt` |
| `mine` | **взято моё** | В develop это место не менялось — берётся ваша версия |
| `mine_add` | **взято моё (добавление)** | Ваши строки добавлены к тексту develop, ничего не удаляется |
| `insert` | **вставлена сущность** | Сущность есть только у вас — вставляется в результат |
| `develop` | **осталось из develop** | Меняли только в develop — остаётся версия develop |
| `meta` | **метаданные файла** | Ид/Наименование/ДатаВремяСоздания — всегда из develop |
| `ws` | **разница в пробелах** | Разница только в пробелах/переводов строк — игнорируется |
| `auto` | **техническое поле** | Код/Порядок — авто-нумерация КД2, не является правкой |

## Команды

### 1. Анализ (только отчёт, ничего не меняется)

```bash
python kd2_merge.py analyze \
  --develop "ПравилаОбменаДанными_УПП-ERP (develop).xml" \
  --mine "ПравилаОбменаДанными_УПП-ERP (изменения).xml"
```

**Что делает:**
- Сравнивает два файла
- Создаёт отчёт `merge_report.md`
- Создаёт шаблон `decisions.txt` со спорными блоками
- **Ничего не пишет в файлы**, только читает

### 2. Слияние (создание результата)

```bash
python kd2_merge.py merge \
  --develop "ПравилаОбменаДанными_УПП-ERP (develop).xml" \
  --mine "ПравилаОбменаДанными_УПП-ERP (изменения).xml" \
  --out "ПравилаОбменаДанными_УПП-ERP (merged).xml"
```

**Что делает:**
- Применяет все изменения
- Создаёт итоговый файл `*(merged).xml`
- Обновляет `merge_report.md` и `decisions.txt`

### 3. Список конфликтов

```bash
python kd2_merge.py conflicts \
  --develop "ПравилаОбменаДанными_УПП-ERP (develop).xml" \
  --mine "ПравилаОбменаДанными_УПП-ERP (изменения).xml"
```

**Что делает:**
- Выводит в консоль только спорные блоки (`need`)
- Полезно для быстрого просмотра

## Пошаговый алгоритм работы

### Шаг 1: Анализ

```bash
python kd2_merge.py analyze \
  --develop "ПравилаОбменаДанными_УПП-ERP (develop).xml" \
  --mine "ПравилаОбменаДанными_УПП-ERP (изменения).xml"
```

После этого откройте `merge_report.md` и посмотрите:
- Сколько спорных блоков (`need`)
- Что изменено автоматически
- Диффы по каждому блоку

### Шаг 2: Решение спорных блоков

Откройте `decisions.txt`. Для каждого спорного блока есть закомментированная строка:

```text
# 34858138 = mine   # / ... / ПередВыгрузкой
```

**Чтобы взять свою версию**, уберите `#` в начале строки:

```text
34858138 = mine   # / ... / ПередВыгрузкой
```

Допустимые значения:
- `mine` (или `my`, `branch`) — взять вашу версию
- `develop` (или `theirs`, `keep`) — оставить версию develop

### Шаг 3: Слияние

```bash
python kd2_merge.py merge \
  --develop "ПравилаОбменаДанными_УПП-ERP (develop).xml" \
  --mine "ПравилаОбменаДанными_УПП-ERP (изменения).xml" \
  --out "ПравилаОбменаДанными_УПП-ERP (merged).xml" \
  --decisions decisions.txt
```

### Шаг 4: Проверка результата

```bash
git diff --no-index "ПравилаОбменаДанными_УПП-ERP (develop).xml" "ПравилаОбменаДанными_УПП-ERP (merged).xml"
```

Или откройте `merge_report.md` — там полная статистика.

## Режим 3-way (с общим предком)

Если файл лежит в Git, можно включить **честное** 3-way слияние:

```bash
# 1. Найдите общий предок
git merge-base origin/develop my-branch

# 2. Выгрузите его версию файла
git show <хеш>:путь/к/файлу.xml > base.xml

# 3. Запустите слияние с --ancestor
python kd2_merge.py merge \
  --develop "ПравилаОбменаДанными_УПП-ERP (develop).xml" \
  --mine "ПравилаОбменаДанными_УПП-ERP (изменения).xml" \
  --ancestor base.xml \
  --out "ПравилаОбменаДанными_УПП-ERP (merged).xml"
```

**Преимущества 3-way:**
- Скрипт точно знает, кто что менял
- Автоматически разрешает многие конфликты
- Блок, который меняли только вы, возьмётся из вашего файла без вопросов

**Без `--ancestor`:** работает режим 2-way с эвристикой «чистого добавления».

## Файл решений `decisions.txt`

### Структура

```text
# Спорные блоки: уберите '#' в начале строки, чтобы взять свою версию
# Формат: <ID> = mine | develop   (комментарий после значения допустим)
# Затем: python kd2_merge.py merge --out merged.xml --decisions decisions.txt

34858138 = mine   # / ПравилаКонвертацииОбъектов / ... / ПередВыгрузкой
# e03959b8 = mine   # / ... / (оставлено develop — по умолчанию)
```

### Правила

1. Уберите `#` в начале строки, чтобы **включить** решение
2. Значение: `mine` (ваша версия) или `develop` (версия develop)
3. Комментарий после `#` — для информации, не влияет на работу
4. Файл автоматически обновляется после каждого запуска
5. Решения **сохраняются** между запусками

## Автоматическое определение файлов

Если в папке есть **ровно один** файл с `(develop)` и **один** без `(develop)`, можно опустить параметры:

```bash
python kd2_merge.py analyze
python kd2_merge.py merge --out merged.xml
```

Но лучше всегда указывать файлы явно для надёжности.

## Сводка по ключевым параметрам

| Параметр | Описание | Обязательный |
|---|---|---|
| `--develop` | Файл develop (основа) | Да (или авто) |
| `--mine` | Ваш файл с правками | Да (или авто) |
| `--ancestor` | Общий предок для 3-way | Нет |
| `--out` | Путь к результату | Для `merge` |
| `--report` | Путь к отчёту (по умолчанию `merge_report.md`) | Нет |
| `--decisions` | Путь к файлу решений (по умолчанию `decisions.txt`) | Нет |
| `--prefer-mine` | Все спорные блоки решать в вашу пользу | Нет |

## Важные особенности

### Авто-нумерация
Поля `Код` и `Порядок` у Свойств и Значений — это **технические поля** КД2, которые пересчитываются при каждом экспорте. Отличие в них **не считается правкой** и всегда остаётся версия из develop.

### Идентичность сущностей
Скрипт ориентируется на `Наименование`, а не на `Код` — у Свойств/Значений `Код` это авто-нумерация, которая меняется при каждом экспорте.

### Безопасность
- `analyze` **не изменяет** файлы
- `merge` **не перезаписывает** исходные файлы — результат пишется в `--out`
- Нельзя указать `--out` с путём к исходному файлу

## Поиск по отчёту `merge_report.md`

Отчёт содержит:
1. **Сводка** — таблица со статистикой по всем статусам
2. **Требуют решения** — спорные блоки с ID и диффами
3. **Детализация по каждому статусу** — с диффами и пояснениями

Для поиска нужного блока используйте поиск по `ID` из `decisions.txt`.

## Часто задаваемые вопросы

**Q: Сколько спорных блоков нормально?**  
A: Зависит от масштаба изменений. Даже 1-2 спорных блока — это нормально, если обе стороны правили один и тот же код.

**Q: Как быстро взять все свои изменения?**  
A: Запустите с флагом `--prefer-mine`:
```bash
python kd2_merge.py merge --prefer-mine ...
```
Или раскомментируйте все строки в `decisions.txt`.

**Q: Скрипт ругается «Разные корневые элементы»?**  
A: Файлы должны быть правилами одного типа (УТ→ERP или УПП→ERP). Не перепутайте файлы.

**Q: Как проверить, что результат корректный?**  
A: Откройте `*(merged).xml` в 1С и проверьте конвертацию. Также проверьте через `git diff --no-index`.
